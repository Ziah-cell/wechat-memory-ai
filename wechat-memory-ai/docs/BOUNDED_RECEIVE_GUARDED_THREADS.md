# 多线程有界观察与退出接管实验

2026-10-09。沿用[475授权](evidence/475-bounded-receive-authorization.json)，将[共享调试对象接管](BOUNDED_RECEIVE_DEBUG_OBJECT_TRANSFER.md)与新线程跟踪、有界字段读取集成到同一实验实现。最终36类场景各3次，**108次符合预期：93次继续运行、12次保留故意触发的原生致命退出、3次目标主动退出**。微信准入仍关闭：真实停顿核算、运行身份及模块绑定等条件尚未完成。

## 实现和范围

新增 [receive_probe_guarded.py](experiments/receive_probe_guarded.py)、[并发夹具](experiments/receive_probe_parallel_fixture.py)、[状态句柄探针](experiments/probe_fixture_freeze.py)、[初始对照](experiments/test_receive_probe_guarded.py)及[最终矩阵](experiments/test_receive_probe_guarded_matrix.py)。原观察器、原失败测试、上一轮接管脚本及产品源码保持原样。

恢复进程在附加前创建并保留同一个调试对象，观察进程在每个线程创建事件继续之前安装自己的硬件执行槽。清理按目标进程句柄枚举线程，保留独立线程句柄并检查所属进程；恢复进程可为已交付但未回复的事件请求重报，再依据实际事件处理。两个角色和目标均为测试脚本自己的同级子进程，入口仍核验夹具身份和四字节虚构函数。

读取沿用既有投影器：单次消息最多512字节、12次读取，正文仅比较40字节虚构标记，端点各最多128字节；结果只含布尔值、计数及使用本次随机密钥的HMAC。实测普通匹配248字节/8次，不匹配168字节/4次，坏指针布局88字节/1次。方向及实时/历史来源始终为 `unknown`。这些数字是当前夹具读量，最大边界的离线投影测试本轮没有重跑。

清理暂停改用独立的进程状态句柄。先在三次对照中确认：夹具暂停后不能回应ping，强制结束持有状态句柄的测试进程后，ping及新的原生调用恢复。首次把创建权限误写为仅 `PROCESS_SUSPEND_RESUME`，三次均遭拒；增加创建所需的 `PROCESS_SET_INFORMATION` 后通过。全部结果见[490](evidence/490-bounded-receive-guarded-baselines.json)。这是本机实测，不是跨Windows版本支持保证。

## 保留的失败及修正

最初用上一轮单线程实现对照新线程标记，得到0次命中；新实现才捕获1次并完成有界投影。不能将上一轮恢复测试当成已覆盖新线程读取。

第一组24次中发现，恢复进程把应用自己的断点异常误当成附加产生的初始断点而吞掉。恢复角色现在不消费“自己的初始断点”。修正后的三次仍被当时测试判失败，因为测试错误地预期ctypes捕获该异常。另做9次无调试器基线后确认：自定义异常可捕获，应用断点退出码为 `0x80000003`，UD2退出码为 `0xc000001d`。据此修正测试预期；没有把致命退出算成继续运行。

随后90次矩阵中有1次并发取消失败。普通并发、屏障同时起跑的局部复验未重现，不能据此宣布修复；提高调用频率后，5次中2次明确出现工作线程single-step异常。失败时清理快照显示自己的槽仍启用、DR6.B0置位、RIP停在入口，而零等待尚未取得对应事件。

这些观察支持的原因是：线程已经触发硬件异常，却在事件完成交付前被清理暂停；此时直接禁用并脱离，可能把未处理异常交给应用。第一版“禁用后解冻并等待”仍失败。进一步诊断取得了真实错误 `own_slot_missing`：异常交付时读到的DR0不再匹配、DR7及DR6已为0，不能依赖禁用后的寄存器保留故障证据。

最终顺序为：冻结时先处理可取得的事件；清除普通线程的槽，但对已触发、尚未交付的自己的异常保留启用槽；释放本次冻结；等待实际事件，设置RF并清除该槽，继续事件，排空已识别的待处理异常后才脱离。若在这些步骤间结束观察进程，恢复进程仍持有调试对象；暂停句柄随退出释放，异常可继续交付。处理的仍须是确切夹具入口的实际单步事件，无关异常交回目标。未知清理错误不会报告成功，实验角色会保留调试对象，等待测试创建者处理；这不是可供真实应用使用的故障恢复策略。

第一次108次扩展矩阵105次通过、3次未满足取消语义：高频调用下，恢复角色已退出，观察角色却先耗尽200次预算，20毫秒轮询通知尚未到达。三次目标均恢复，但不能证明该退出被及时检测。最终改为在每轮事件循环检查保留的恢复进程句柄，5次定向复验通过，再重跑完整矩阵。失败、版本及寄存器布尔诊断见[491](evidence/491-bounded-receive-guarded-races.json)。

最终矩阵有2次实际进入解冻后的遗留异常排空分支；另有4次在清槽/解冻边界结束观察进程后，恢复角色收到了仍带自己启用槽的单步事件。成功要求新的主/新线程调用、增长的心跳、全部并发工作线程完成及无stderr，不能只凭“脱离成功”返回值。目标自主执行，无等修好后才允许下一调用的握手；工作线程异常会记录并重新抛出，不吞掉。

这是有限样本，不证明所有调度或指令间隙。恢复角色仍故意延迟200毫秒接手，验证的是保留调试关系的效果。`max_event_processing_ms` 仅计事件处理函数时间，未计事件产生到取得之间的停顿；`cleanup_ms` 也不含故障检测和恢复前延迟。最终清理局部最大1.822毫秒不能用来宣称整次停顿小于100毫秒。

## 依据与继续条件

状态句柄及线程枚举声明来自固定提交的 [System Informer phnt/ntpsapi.h](https://github.com/winsiderss/systeminformer/blob/9cdd0426e0843e80cabef27f148cee0281fa0883/phnt/include/ntpsapi.h)，仅保存文本并核验哈希，没有安装或执行上游代码。创建权限及最后句柄释放行为参考研究者的 [NtCreateProcessStateChange](https://ntdoc.m417z.com/ntcreateprocessstatechange) 和 [NtChangeProcessState](https://ntdoc.m417z.com/ntchangeprocessstate) 文档；它们属于第三方研究。事件继续状态参考微软 [ContinueDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent)。本实现依赖的Native接口与跨进程接管方式未取得微软稳定性保证。

下一步仍在夹具中完成实际暂停区间和总量核算，包含排队、附加、清理及故障接手；不能用缩短日志计时或扩大预算绕过原条件。随后还需核验初始断点分类、系统调用失败及两个角色同时退出等未覆盖边界，并完成真实进程身份、固定模块/入口、最小化状态和本次随机标记绑定。当前静态虚构标记及四字节夹具校验不能用于微信。不存在直接传入微信PID的运行方式，也不请求新测试消息。
