# 4.1.15.50：逐条消息来源核查

## 2026-10-09 续查：scene 消费规则与集合写入

[468](evidence/468-inbound-scene-consumers.json)接通了 `scene` 的三个具体消费者；[469](evidence/469-inbound-key-set-writers.json)接通了前轮集合的三处插入调用及完整键选择规则。结论仍是：**两者都不足以作为实时/历史分类器，不能据此开启自动回复。** 下方 464–467 保留前一阶段的发现；其中“消费者、写入点未闭合”的部分由本节补充。

### scene 的比较结果不是统一的新旧枚举

以下只列函数已到达所选 `scene` 分支、对象稳定、正常返回时的结果；这些函数还有其他前置条件。

| 消费者 | 已核数值规则 | 实际调用位置 |
| --- | --- | --- |
| `abce70` | 无其他覆盖条件时，scene 属于 `{0,2,9,15,17}` 返回 true；解析对象的 `+dc` 掩码条件也可直接令其 true | `2acb300` 的条件分支决定是否继续调用 `2acf6a0`；没有新旧枚举名称依据 |
| `abcf40` | 解析对象存在且 scene=53 才返回 true | `17cb2c0` 在其他门通过后决定是否加入一条支路的消息集合；不是所有普通来信都走这里 |
| `17c7fb0` | 到达尾部分支后，scene 属于 `{0,2,9,17,53}` 或解析对象为空时返回 false；其余 DWORD 值返回 true | true 分支会复制消息并修改副本的字段，再按条件进入后续处理；不等同于丢弃历史消息 |

第三项的返回方向尤其不能看反：位掩码命中后返回的是 false。scene=15 在第一、第三项都可为 true；scene=53 在第二项为 true、第三项为 false。它们是不同用途的谓词，不能合并成一个 `is_live`。

`scene` 也没有覆盖所有缺值情况：`a78d60` 新建解析对象时清零，原始字符串为空会跳过解析；`2353c30` 找不到 `scene` 节点时也跳过写入。因此在这条新建对象路径，缺字段和显式 0 可以到达相同存储值。这个事实已足够否定“仅见 scene=0 就证明来源已认证”；不需要访问真实消息。重用已有对象时的旧值另计，本轮没有断言它总被清零。

### 集合记录的是派生键，不是历史同步游标

`23ae820`、`23b8fb0`、`23bc6f0` 的选定路径都调用 `a7c8e0` 构造键，然后将它交给 `23b8ba0`，集合地址均来自服务成员 `+148` 指向的状态再加 `+140`。这与 `23be9a0` 查询并删除的集合布局一致。前两类包装调用的返回、消息结构更新不等同于数据库事务提交；本轮未认证整个大型函数的业务名称或全部执行条件。

键的具体构造链为 `a7c8e0 → 22e9900 → a3eb00`：

| 条件 | 最终键 |
| --- | --- |
| 消息 DWORD `+144=0`，且消息字符串 `+2c8` 非空 | 直接使用 `+2c8` 字符串 |
| 其他情况 | `a7b9f0` 返回的字符串 + `_` + DWORD `+164` 的无符号十进制 + `_` + DWORD `+144` 的无符号十进制 |

`22e9900` 还复制了消息 QWORD `+150`，但这个格式化函数不消费该值；当前 AddMsg 字段 12 对应的内部 QWORD `+148`也不是上述选择/格式化输入。这里不把 `+144`擅自命名为已认证的本地消息 ID，也不把选择出的字符串当作已认证账号或联系人。实际字段取值、生成代次、跨账号唯一性仍未知。

插入 helper 会更新已有键对应的链表节点；未命中时还存在受参数控制的裁剪调用。消费 helper 则命中后移除节点。因而第二次查不到同一键可以只是第一次已消费；“不在集合中”不证明没有收到过，也不证明此次是实时消息。这里没有建立持久历史水位、完整重放集合或数据库提交边界。

本轮结束这两个字段作为**单独自动回复准入判据**的定点核查。后续应回到具体采集器方案，要求来源本身提供可解释的初始同步、重连和逐条交付语义；不能继续通过猜 scene 数值、换一个集合或填 `verified` 来生成依据。没有新来源证据前，原有静态事件链只作研究参考，不进入产品。发送能力仍需单独验证。

[470](evidence/470-inbound-consumers-validation.json)记录新鲜字节、选定指令与纯数值推导复核，不是微信执行测试或独立审查；[471](evidence/471-inbound-consumers-checkpoint.json)保存状态。产品 0.1.22、自动回复关闭、无可运行最小化适配器，本轮不操作微信。

## 同步模式进入延迟处理体后发生什么

[465](evidence/465-inbound-deferred-text-gate.json)接续 [434](evidence/434-inbound-sync-mode-propagation.json)已绑定的批次参数：`17c9c50` 将 `mode==19` 捕获到表 `9289118` 对应闭包的 `+10`；表槽 `+10` 指向 `185ede0`。

该体遍历捕获的消息 shared-pointer 列表。经过前置门后，`17c5700`按类型/子类型查找 handler。只有 handler 存在，且其虚槽 `+48`返回 true，才会读取闭包 `+10`，并将其作为第三参数交给 handler 虚槽 `+40`。

默认文字注册仍以 [381](evidence/381-send-handler-registry.json)为条件；本轮重新核对构造器 `38c9450`安装表 `96b69e8`：

| 文字处理器槽 | 具体实现 | 本轮意义 |
| --- | --- | --- |
| `+48` | `af10`：`xor eax,eax; ret` | 固定 false，跳过这里接收模式参数的调用 |
| `+40` | `38d3c90` | 释放传入的 shared-pointer 引用后返回 true；本体不读取模式参数 |

因此，**这条默认文字分支不能补成“模式区分实时文字来信”的判据**。这不否定上游批次准备会使用该模式，也不覆盖其他 handler、注册覆盖、运行时实际 receiver 或其他事件分发路径。表查找和方法存在不证明本机已经订阅到事件。

另一个容易混淆的门是 `23be9a0`。闭包在 handler 调用前后用它查询一个内部字符串键集合；命中时会移除元素、释放节点并返回 true。前一次命中会跳过该消息的这段处理；后一次命中才进入所选后续分发。它是有副作用的查询/移除，不能当作可反复读取的布尔 getter，更不能叫作“历史消息判定”。集合写入来源和键语义本轮未认证；不能从两个调用结果推断数据库已提交或消息刚收到。
