# 自建发布器持门异常与线程隔离

2026-10-11；沿用用户继续开发授权，实施于 implementation。仅新增自建实验，不更改冻结源码、产品、监听器或微信进程。

1. 先建立独立驱动：正常、持门后、写入序号及16字节后、完整记录写入但游标提交前、游标提交后、双线程重入、双线程含原异常，共7类。缺实现失败留档。
2. 从 capture_faults_fixture.c 另存变体。新发布函数在成功取得 gate 后使用 finally 释放；在上述内部位置通过既有受保护页复制点产生真实读异常。只声明这些点的异常展开，不声明实际共享写指令出错或任意内存损坏恢复。
3. 场景和重入深度均按线程保存。测试专用事件确定地使线程1在深度1暂停，线程2完成嵌套调用，再放行线程1；事件不在发布器持门区。检查两个工作线程结束时深度0、不同线程ID、原返回及记录顺序。该测试同步不作无阻塞或时延承诺。
4. 同一EXE提供不释放门、全局重入深度两种故障对照；沿用正确行为断言，必须留下失败。最终7类各3次，所有子进程实际退出。
5. 原生消费者和既有SQLite接收器继续独立运行。检查部分记录不推进游标、故障后状态停用；已提交记录只断言随后消费者拒绝，不声明撤销更早交付。正常TLS场景预期id2、id1、id3；异常TLS场景id2、id3。
