# 正常打开窗口的实测记录

2026-10-12，用户确认新旧测试账号不同，完成旧号只读对照后，明确选择继续使用旧号，并授权唯一测试好友的正文与遮挡读取。全程不输入、不发送、不调用模型、不写真实记忆；没有保存正文、联系人、绑定标识或图像。

**当前结果：旧号在非前台、部分遮挡下静态读取成功，完整遮挡仍待验证。** 575 中连续 3 次视觉快照均有 7 个列表项、3 条文本；联合读取取得 3 条非空文本。每次窗口未最小化且不在前台，9 个采样点中 6 个命中其他窗口、3 个命中目标。每次调用前后的前台窗口相同，但没有持续焦点事件监测，不能据此断言中间绝无变化。

视觉结果为 1 条来信候选、2 条方向未知，另 4 项非文本。576 元数据检查发现 2 条文本控件的边界超出列表区域，与 `geometry_invalid` 的保守停止条件相符；不降低几何门槛、不猜测方向。无滚动模式，底部/历史边界未知。输入框暴露可写 ValuePattern 和 TextPattern；发送按钮标签候选有 InvokePattern，但当前禁用。仅检查能力，没有设置值、调用发送或验证其焦点行为。

559–570 中新号的浅层结构统计不证明整个 UIA 树都没有输入控件，也不证明独立窗口没有打开。该号检查不能建立私聊绑定，按规则停止。新旧号客户端版本均为 4.1.15.50；此前权限检查双方均为 medium。

后续检查发现一个诊断缺口：原代码仅在 UIA 标识匹配目标后才检查最小化，而 561 的统计也仅记录已识别私聊窗口的最小化状态，不能据此断言当时所有窗口都正常打开。现已在 UIA 访问前增加“全部微信窗口最小化则停止”的检查。566/568 证明本轮运行时全部最小化，**不追溯证明 559–562 当时也全部最小化**，也没有证明 UIA 接口差异。已请用户恢复授权独立窗口，再切回其他应用，保留正常打开状态；不自动恢复、不反复要求重新开窗。

用户随后回复已准备，569/570 表明现在确有正常窗口，但三种 UIA 客户端均未取得私聊根标识。该结果不支持“仅更换 .NET UIA 为 COM UIA 就能解决”的假设，也不能证明微信整个控件树永久不可访问。根据 [Microsoft UIA provider 文档](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview)，只有通用窗口信息而缺少应用 provider 时，自定义控件可能无法被客户端访问；这是对本轮表现的解释，不是对账号策略或微信内部原因的确认。未调用 MSAA/LegacyIAccessible，也未修改系统或微信设置。

571 的 Win32 类假设没有命中，因此未执行下层结构遍历。没有将类名、标题或“唯一正常窗口”替代产品的私聊绑定。Computer Use 工具初始化故障独立于微信本身；不把工具不可用当成微信不支持 UIA 的证据。历史 69 记录同一客户端版本在用户重新登录后可读，尚不足以证明重新登录一定有效。

用户随后明确确认**当前换了测试账号**（573）。历史账号曾可读、当前账号的正常窗口不可绑定，是两个账号在不同时间的观察，尚不是同环境的受控对照。账号或登录会话相关的可访问性差异因此值得优先核查，但不能宣称账号被限制、权限被封或原因已确定。[pywechat 开发者的 4.1+ 说明](https://github.com/Hello-Mr-Crab/pywechat/blob/main/Weixin4.0.md)也报告不同账号的 UI 树可见性差异；这是第三方开发者经验，不是微信官方解释，也不是对本机当前账号的诊断结论。没有按外部教程修改注册表、启用讲述人、降级或安装程序。

经用户授权并手动准备，574 旧号对照成功，说明当前机器与读取方法可以取得私聊根标识。该结果支持账号/登录会话相关差异，但未完成新号→旧号→新号复查：用户要求不用新号，并进一步明确授权旧号的正文和遮挡只读验证。当前以旧号为目标，不再等待切回新号，也不将新号失败解释为永久限制。575/576 已在新的授权范围内执行。

现有读取器没有激活、置顶、恢复、键鼠输入或发送 API；PrintWindow 仍限绑定且未最小化窗口。575 已记录目标非前台和部分遮挡，前后前台句柄相同；9 点采样不是全窗口逐像素覆盖证明，也不能推广到完整遮挡、最小化、锁屏或后台长期稳定运行。

发送仍没有已验证的无焦点路径。576 的可写 ValuePattern/InvokePattern 只说明控件声明了接口，不证明实际操作成功、不抢焦点或发送到正确联系人。现有 ReadOnlyWeChatSource.send 明确拒绝；不能采用抢焦点输入作为新方案的隐式回退。
