# 正常打开窗口的实测记录

2026-10-12，用户两次确认准备并最终确认已打开授权好友的独立窗口。本次不操作微信窗口、不输入、不发送、不调用模型、不写真实记忆。

目标是微信正常打开且其他应用可保持在前台。只读检查计划依次取得同一窗口的视觉计数、UIA 能力、联合正文/方向计数，再用只读 Win32 状态比较前台句柄和窗口内 9 个点的遮挡情况；不保存正文、绑定或图像。实际在第一步身份发现阶段停止，**尚未执行视觉捕获、联合正文读取和遮挡采样**。

| 证据 | 实际结果 |
| --- | --- |
| [559](evidence/559-open-window-live-read.json) | 首次没有识别到唯一独立窗口，返回 private_window_not_unique，0 快照 |
| [560](evidence/560-open-window-live-read.json) | 用户打开独立窗口后仍返回同一原因，0 快照 |
| [561](evidence/561-open-window-structure.json) | 2 个可见微信窗口，根标识均为空；直接子控件合计 4 个，未见列表/输入框标识，0 检查异常 |
| [562](evidence/562-open-window-live-diagnostic.json) | 新增诊断明确返回 window_identity_unavailable，0 快照；检查开始和结束时前台窗口相同 |
| [566](evidence/566-open-window-uia-comparison.json) | 继续检查时发现 2 个窗口均已最小化；原计划的 .NET/COM UIA 比较全部跳过，未读取根属性、正文或像素 |
| [568](evidence/568-open-window-preflight-live.json) | 修正发现顺序后实机返回 window_minimized，0 快照；检查开始和结束时前台窗口相同 |

浅层结构统计不证明整个 UIA 树都没有输入控件，也不证明独立窗口没有打开。当前不能安全建立原窗口绑定，因此保持停止。版本为 4.1.15.50，双方进程权限均为 medium；这些观察尚不足以解释本次和既往可读会话的差异。

后续检查发现一个诊断缺口：原代码仅在 UIA 标识匹配目标后才检查最小化，而 561 的统计也仅记录已识别私聊窗口的最小化状态，不能据此断言当时所有窗口都正常打开。现已在 UIA 访问前增加“全部微信窗口最小化则停止”的检查。566/568 证明本轮运行时全部最小化，**不追溯证明 559–562 当时也全部最小化**，也没有证明 UIA 接口差异。已请用户恢复授权独立窗口，再切回其他应用，保留正常打开状态；不自动恢复、不反复要求重新开窗。

现有读取器没有激活、置顶、恢复、键鼠输入或发送 API；PrintWindow 仍限绑定且未最小化窗口。源码满足不主动抢焦点的设计约束，实测只确认本次失败检查前后前台窗口相同。它不等于持续焦点监测，也不证明目标窗口已处于非前台/被遮挡状态。

发送仍没有已验证的无焦点路径：未到达可绑定输入控件，未检查到可用写入/发送操作，更未执行动作。现有 ReadOnlyWeChatSource.send 明确拒绝；不能采用抢焦点输入作为新方案的隐式回退。

下一阶段先在已恢复、正常打开的授权窗口中验证普通 UIA 可访问性；若仍缺标识，再比较 .NET 与原生 COM UIA 的只读根属性。随后在明确绑定的授权窗口中验证静态读取与新事件、记录实际非前台/遮挡状态，再评估发送控件与焦点条件。身份、历史和去重边界需单独完成后才能接入 Engine；不能把离线桥接当成真实微信已接通。不恢复 MSAA、最小化、Hook 或内部数据库研究。
