### 不能靠补取原始行修复身份

`get_message_row(user, local_id, local_type=None)`（db.py 1923–1965）按local_id查询所有分片，可选过滤类型，然后取sort_seq最大的行。它没有接收原始分片或预期server_id来确认关联；`get_message_rows_for_media`虽返回全部匹配，仍不带分片定位。

[462](evidence/462-db-raw-metadata-validation.json)新增三个自写内存SQLite反例，全部通过：另一个分片的更新行覆盖原消息的元数据；同类型碰撞不受类型筛选保护；同seq碰撞的选择随分片遍历顺序变化。最后一种是合成顺序变化，不宣称本机一定改变分片顺序；即使顺序固定，也不能证明取到监听时的那条消息。需要从首次读取就保留身份，不能事后按local_id补取source再放入回复核心。

## 数据获取：先证明入口，再开真实观察

候选读取的是账号目录下 `db_storage/message/message_N.db`、相关WAL以及 `message_resource.db/SenderName2Id`。目标表名为 `Msg_`加username的MD5（db 1628–1639）；这个hash只是表定位，不认证好友身份。

未来可采用的获取方式按以下顺序判断，而非自动回退：

1. **优先：兼容该构建的数据库连接与读事务/备份API。** 必须先有固定实现、格式/加密兼容依据及取得连接的授权。SQLite的读事务和备份API能提供其数据库的快照语义，但标准Python sqlite3不能因此直接打开微信加密库；此处尚无经验证的 .50 连接实现。[SQLite隔离](https://www.sqlite.org/isolation.html)、[备份API](https://www.sqlite.org/backup.html)。
2. **原始主库+WAL复制仅作备选研究。** 需要证明主库与WAL代次一致、合法帧连续前缀、最后提交边界、并发checkpoint处理与文件集完整性。两次mtime/size相同、主库可打开或quick_check通过都不够。不能直接沿用候选的旧副本/仅主库回退。
3. 各分片和映射库分别可读，不自动等于跨库原子快照。若没有共同捕获边界或可验证的映射稳定性，身份结果保持不明；不把多个独立时间点拼成已认证事件。

当前只实现了**自写内存SQLite的固定快照分页实验**，输入全部由脚本生成；没有真实文件输入口。其 `(sort_seq,local_id)` 游标在每个分片分别推进，全部成功后才返回结果；243组比较与独立全量排序一致。前提是单片该二元键唯一、非NULL，快照固定，分片清单完整；这些前提没有在 .50 实机认证。它不是增量采集器：案例04证明跨轮复用游标仍漏晚到低序号行。

## 原始字段、身份与历史策略

后续观察器需由具体读取实现保留：来源账号绑定、快照/分片代次、目标原始username、分片标识、表标识、local_id、server_id、sort_seq、local_type、real_sender_id、create_time及必要文本。分片路径和账号值只留内存；报告仅输出计数。来源账号绑定不能由目录名推断，候选现有入口未满足此项。

只接受指定单个私聊目标，禁用 `add_all`、昵称搜索回退、自动换账号和自动扩展文件范围。未来运行前应核验登录账号与指定数据库的关联，并用同一授权目标的新自身/对方样本验证映射。方向只可来自同一有效映射中的明确账号/好友关系；空映射、数字回退、正文前缀、第三方发送者均为unknown，不取“非self即peer”。

观察定位键为 `(账号代次,分片代次,表,local_id)`；业务去重候选为 `(已认证账号,已认证私聊目标,server_id)`，必须另证ID非零及作用域。原始键一致却内容/方向冲突时停止；server_id=0不能改用正文hash冒充真实身份。这些只是设计要求，目前未赋予任何记录accepted状态。

首次完整快照全部作为历史基线，零交付。重新启动、换号、文件集变化、分片失败、快照降级、身份映射失效均关闭本代次；再次观察须完整建立新基线，停机积压不补进回复核心。持久记录只能用于防重/审计，不能恢复“正在实时监听”的资格。

**即使上述措施都实现，基线之后首次见到也只能叫newly_observed。** 本轮证据无法排除实时消息与晚到同步产生相同观察字段的情形；案例12人为构造相同观察与不同来源假设，不是两次微信实机观察。服务器ID非零、create_time较新、seq增大、固定等待、随机标记和数据库提交时刻都不单独证明实时到达。候选所查接口没有逐条来源类别/实时边界证据；原始source/packed_info_data是否包含可用区别仍未认证，不能由公共投影缺字段推断整个数据库绝无相关信息。必须新增有依据的来源关联，或继续拒绝交付；不能仅以“换新基线”声称历史问题已解决。

## 事件所有权、有界交付和停止

后续若两个否决点获得依据，观察器采用单独、无模型和发送权限的工作进程；不直接托管上游Listener或任意用户回调。工作进程独占数据库连接和快照文件，行复制成不可变值后才释放连接；主进程只接脱敏统计。这里的进程隔离是方案，尚未启动任何观察进程。

建议首个诊断版本设：单目标、最长60秒、每页最多200行、累计最多10,000个定位键/8MiB（任一触限即停止并丢弃未完成批次）、有界交付64项/1MiB（任一触限即失效，不覆盖旧项）、每轮最长5秒。数值是待测的资源上限，不是性能结果；没有必要先把模型回调纳入队列。

停止顺序明确为：先撤销本代次交付资格 → 停止读新页 → 丢弃待交付项 → 当前本地读取结束并关闭连接 → 退出工作进程 → 父进程确认该进程退出。超时则只终止自己创建的工作进程并再次确认退出；未确认则报告stop_unconfirmed并禁止开始下一代次，不操作微信进程。不能以sentinel已入队、pending=0或join返回宣称停完。[Python Thread.join契约](https://docs.python.org/3/library/threading.html#threading.Thread.join)。

该方案不在微信内部注册回调，因此不要求复制NewSync内部停止字段；它只证明自己创建的资源已退出。真正的微信回调来源若另行加入，须另证其解绑和排空，不能借用此进程退出结果。
