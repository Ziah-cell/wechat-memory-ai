# 有界观察器：强制退出后的断点残留已定位，当前方法不进入微信

2026-10-09。延续[475的授权](evidence/475-bounded-receive-authorization.json)，本轮只操作本项目创建的测试子进程。**问题已定位，但没有实现满足原门槛的自动恢复；当前直接使用 DbgEng 硬件断点的观察器仍不能进入微信。** 这不是等待用户再次许可，也不表示所有接收方法都不可行。

## 新证据回答了什么

上一轮[原生测试](BOUNDED_RECEIVE_NATIVE_RESULTS.md)已发现强制结束观察器后，目标再次调用时发生单步异常。本轮增加诊断脚本（历史源码路径 `experiments/diagnose_receive_probe_crash.py`，已删除），直接读取自己创建的夹具主线程状态：先核对线程所属 PID，再成对 SuspendThread / GetThreadContext / ResumeThread。AMD64 CONTEXT 按固定微软头文件使用16字节对齐、1232字节缓冲，只请求控制和调试寄存器；不重新附加来读取，不捕获目标的单步异常，不读取用户进程。

| 对照 | 次数 | 结果 |
| --- | ---: | --- |
| 未附加观察器的基线 | 1 | 调试寄存器为零，调用和心跳继续 |
| 命中一次后正常取消、分离 | 1 | 调试寄存器恢复为零，调用和心跳继续 |
| 收到 armed 后立即强制结束，尚未要求调用 | 3 | 退出后 DR0 仍指向夹具函数、DR7=0x1，原暂停计数仍为1；后续调用未完成 |
| 一次调用已返回后强制结束 | 3 | 退出后 DR0 保留、DR7=0x401；下一次调用均产生单步异常、退出1 |
| 一次调用已返回，再等400毫秒后强制结束 | 3 | 同样残留，下一次调用均产生单步异常、退出1 |
| 强制结束后，在允许下一次调用前主动禁用残留断点 | 3 | 读取确认调试寄存器为零，后续调用和心跳继续 |

这是14次**诊断对照**，不是14项恢复验收通过。前11次诊断进程返回1，因9次强制终止对照未恢复；后3次因果对照返回0，不能据此打开微信实验门槛。全部原始结果的哈希、脱离实际地址的快照及初次诊断配置错误保存在[479](evidence/479-bounded-receive-crash-registers.json)。

在已完成过调用的6次失败中，观察器退出后 EFLAGS.TF 均为0，线程原暂停计数为0，但 DR0 指向原函数且 DR7 的第0槽仍启用。这将所测失败定位到**仍启用的硬件断点**，不是仅凭“单步异常”猜测 TF 残留。400毫秒对照排除了“再等一个250毫秒片段就自行消失”这一具体假设，不外推其他时间和系统的全部行为。

## 手工禁用为何不能作为恢复实现

因果对照在暂停夹具主线程后，确认只有自己的第0槽启用、地址等于夹具函数，再向 SetThreadContext 提交仅关闭 DR7 第0槽使能位的上下文；其他调试字段照抄，不修改 EFLAGS、RIP、代码或消息内存。随后读回时，Windows 返回的调试寄存器全为零。不能说操作系统必定原样保留提交上下文的其他位。

这3次成功依赖测试脚本控制调用顺序：**先禁用，再要求目标执行**。真实客户端可以在守护进程发现故障、暂停线程或清理之前再次进入该函数；原始失败路径已展示这个次序的后果。因而添加轮询守护进程、增加等待、只保证进程暂时存活，均没有解决当前恢复要求。armed 后立即结束的3次结果还表明，已输出 armed 不证明引擎已让目标线程完全恢复运行。

本轮没有把手工禁用加入观察器，没有修改原始失败测试、增加异常吞噬或 expectedFailure。只为夹具 ready 输出添加自己的主线程 ID，供测试脚本核对和读取；观察器源码保持上一轮版本。

## 原始失败仍保留

另行运行现有测试中的3项：固定 SDK 接口槽位核查通过、正常标记命中/分离通过、**原始强制结束后恢复测试仍失败**，合计2通过、1失败、0错误，命令退出1。该失败测试没有调用新增的线程读写诊断代码，因此不能将它归因于诊断时的暂停操作。详情见[480](evidence/480-bounded-receive-crash-validation.json)。没有重跑上一轮完整12项，也没有重跑产品全回归或17项离线投影。

接口依据为微软 [GetThreadContext](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadcontext)、[AMD64 CONTEXT](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-context)、[SetThreadContext](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setthreadcontext) 及 [固定 winnt.h](https://github.com/microsoft/win32metadata/blob/76c04c2021ef4a831a6f1e06d9566002d746139b/generation/WinSDK/RecompiledIdlHeaders/um/winnt.h)。文档要求暂停线程后读取或设置上下文；调试器退出行为的[选项文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-debugsetprocesskillonexit)不能替代本机断点清理实测。第三方头文件仅保存在忽略的 data 目录，没有安装 SDK。

## 当前决策与下一步

当前单进程 DbgEng 硬件断点方案的异常退出要求未满足，结束“只修补普通清理或延长等待就可进入微信”的尝试。保留夹具、失败测试和正常分离实现作为后续对照；不把它包装成可用适配器，也不在真实微信上验证恢复猜想。

若继续这条方法，必须先提出并用自建程序证明一种不依赖“目标等到清理之后才再次执行”的生命周期方案；仅将观察器改名为代理或增加进程数量不算解决。没有这样的机制时，下一项应重新选择具备可验证退出行为的具体采集来源，而不是继续扩展消息偏移或重跑已失败的同一测试。任何替代来源仍须解决账号/目标、方向、初始同步与重连、去重和独立发送结果；当前接收研究不证明最小化发送可用。

[481检查点](evidence/481-bounded-receive-crash-checkpoint.json)保存本轮边界：产品0.1.22、自动回复关闭，旧监听保存停止状态；没有微信附加/内存读取、窗口操作、密钥或聊天数据库访问、真实发送、Jev或其他判断模型调用。全部被暂停、读寄存器、写调试上下文或强制结束的对象均为本项目自建子进程；3个挂起夹具仅在测试结束时由其创建者清理，不是恢复成功。
