# 真实共享槽写异常与发布隔离

2026-10-12。在新的自建 Windows x64 变体中，实际将共享槽所在视图页改成只读，让正常写指令触发访问异常。最终 19 类各 3 次，**57/57 通过**；其中 51 次真实写访问异常，45 次符合窄过滤条件并保留原调用结果，6 次不符合条件而向外传播。另有 3 次嵌套原调用读异常向外传播。这些传播异常由最外层测试观察器记录，不算生产过滤器处理成功。

独立中继提交 **333 条完整记录**，57 个会话全部持久结束；部分写入记录和终态后新增均为 0。285 个测试进程退出码齐全，57 个目标自主清理，1365 次原调用正常返回。382 项产品离线测试通过。产品与真实微信没有接入本变体。

## 故障边界与实现

旧实验的指定异常来自复制读指令；旧布局的控制字段和槽位又在同一页。直接把整页设为只读，会同时破坏异常处理中对停用状态的写入。因此新协议 v3 固定为两页：第一页控制字段，第二页 8 个槽位。编译期断言记录起点为 4096、总大小为 8192；运行时核验控制页为 PAGE_READWRITE、被保护的记录页为 PAGE_READONLY。

槽位的每次 64 位写入使用同一个汇编叶函数 `XCHG [RCX],RDX`。最终每次运行都记录站点长度 3 和实际机器码 `48 87 11`。这是 Windows x64 限定实验；内存 XCHG 的锁定语义依据 [Intel 指令手册](https://cdrdv2-public.intel.com/782156/325383-sdm-vol-2abcd.pdf)，不是跨平台 C 原子证明。

局部处理必须同时满足：实际 EXCEPTION_ACCESS_VIOLATION、操作标志为写入 1、PC 精确等于该写站点、故障地址等于本线程刚准备写入的槽字段、地址在已知记录区且 8 字节对齐、当前捕获深度为 1、写门仍持有。Windows 异常记录提供操作类型和故障地址，详见 [EXCEPTION_RECORD](https://learn.microsoft.com/en-us/windows/desktop/api/winnt/ns-winnt-exception_record)。页保护变化仅为实验注入；不在异常处理中修复权限、重映射或跳过故障指令继续执行，参见 [VirtualProtect](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualprotect)。

原调用先返回，再发布复制出的数据。匹配的写异常沿 finally 先停用采集、再释放写门，并清除线程中的待写地址与捕获深度；Hook 返回先前保存的原结果。测试每次比较完整参数对应的原返回值，并分别计数原调用返回和工作线程收到的成功返回，避免用“原调用执行过”冒充“结果已返回”。

## 最终矩阵

每个目标接受 24 次有限工作，间隔 40 ms；以下每类重复三次。主调用工作线程为一个，ACK 服务线程和外部只读消费者、中继、接收器独立运行。

| 场景 | 每次实际结果 |
|---|---|
| 健康跨圈 | 24 个正确返回、24 条提交及 ACK |
| 首条记录的 7 个写点 | 依次在奇数 stamp、seq、4 个正文 word、偶数 stamp 写入处实际失败；正确处理 1 次，24 个原结果仍返回，published/ACK/库行数均为 0 |
| 跨圈复用的同 7 个写点 | 前 8 条已提交和 ACK；写 seq9 实际失败，前缀保留 8 行，published 和 ACK 均停在 8 |
| 相同写操作、其他 PC | 实际写异常不被局部处理，外层测试观察器收到 1 次，工作线程成功返回 23 次；部分槽不交付 |
| 相同 PC、记录区外地址 | 实际写异常不被局部处理，外层收到 1 次，成功返回 23 次；记录页保持可写，也不能误当成允许处理的槽故障 |
| 嵌套原调用读异常 | 操作标志 0、PC 在原调用区域；继续向外传播，23 个后续原结果返回，虚构 id2–24 共 23 行提交 |
| 控制器退出后跨圈写故障 | 真正结束嵌套启动控制器，目标继续 24 次并自行清理；seq9 最后一个写点失败，保留 8 行 |

在每个写点，测试和独立审计分别按已完成的写入步骤重建 stamp、seq、4 个 word，逐值比较实际部分槽内容。第 7 个写点失败时，正文甚至已全部复制，但 stamp 仍为奇数，发布游标不能前进。既有完整提交不会因后续异常被撤回。

最终 45 次允许处理的写异常全部保留 24 次正确返回，写门为 0，每次工作结束后的捕获深度和待写指针均清除。6 次拒绝的写异常加 3 次原异常由测试观察器接住，保留“该次调用未正常返回”的事实。285 个进程为 282 个退出 0、3 个指定控制器故障注入退出 1；没有靠外部结束目标补做清理。

333 次成功 ACK 都有本中继此前收到的提交回执。57 个终态证明均为 `same_process_signaled`，全部保留 `tail_unknown=true`。观察到的丢弃区间为 0，不代表故障后的未发布输入没有损失；此次没有可信生产者最终高水位。

## 失败保留与独立审计

缺实现预检的真实失败单列保存。两次原生构建均成功，所有编译输入、输出和 EXE 均保留。第一版用于首批六项正向及第一轮负对照；第二版增加实际指令字节记录并修正文档注释，最终矩阵与第二轮负对照使用同一 EXE。

两轮六项负对照共 12 项均按正确断言失败：旧读过滤器漏接真实写异常，导致已计算的原结果有一次未返回工作线程；漏释放门留下 gate=1；提前发布游标留下 published=1 而 stamp 仍为 1；宽泛过滤器分别吞掉其他 PC、其他地址和嵌套原调用异常。提前发布对照仍被其他停用/读侧检查挡住，实际数据库为 0 行，不能声称发生了错误入库。失败没有改为成功的 expected-failure。

全部进程矩阵 75 项中 63 项匹配、12 项失败；375 个进程均有真实退出码。独立审计不导入被测模块，核对归档源码、构建、异常标志、槽内容、原始 ACK 顺序及每个进程的退出。全部 75 库共 388 行、75 个结束会话；数据库连同 WAL/SHM 复制后只读核验，原件哈希不变，部分交付及终态后新增均为 0。原 70 研究源码、29 产品源码、24 分析脚本、365 证据和 783 个冻结旧文件保持不变。

## 严格限制与下一项

只证明映射仍有效、控制页仍可读写时，**已知共享槽写站点**的只读页访问异常能按指定规则处理。没有证明控制页本身失效、任意地址失效、任意对象寿命、取消映射、内存破坏或任意异常恢复。VirtualProtect 是实验注入，不能从这些运行声称 Hook 无系统调用或有严格延迟上限。

本轮只有一个原调用工作线程。外部消费者虽独立运行，但没有确定调度第二生产者、ACK 服务与故障展开之间的每种竞争；旧读异常的竞争结果不能替代新写异常验证。下一项应在新的自建变体加入这类确定交错，尤其检查过滤器决定、先停用后解锁、待写 TLS 隔离及读侧发布边界。

OS 死亡与 SQLite COMMIT 仍非原子；PID 缺席/复用、真实权限与枚举错误、热装卸、CFG/CET 和真实微信身份/ABI仍未证明。旧断点双角色失败保持失败，475 不扩展实机注入授权。产品仍为 0.1.22、自动回复关闭、旧监听停止，id40 此前暂停状态不变；没有真实微信/窗口/密钥/聊天库/发送/模型/子代理/新工作树操作。
