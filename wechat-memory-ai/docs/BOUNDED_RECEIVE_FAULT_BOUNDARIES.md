# 双角色退出失败与初始断点分类实验

2026-10-09。延续[授权](evidence/475-bounded-receive-authorization.json)及[生命周期集成](BOUNDED_RECEIVE_TIMING_LIFECYCLE.md)。本轮确认：**当前共享调试对象、双角色恢复方案仍不能进入微信**。两个辅助进程均退出后，已启用的目标硬件断点不会随调试关系一起消失；最终30次恢复验收中12次失败。另一个初始断点误分类问题已复现，并有仅限本机夹具的分类候选通过15次对照，但它不修复双角色退出失败。

## 两个角色均退出

新验收脚本（历史源码路径 `experiments/test_receive_probe_dual_loss.py`，已删除）只创建、结束自己的夹具和观察/恢复进程。先请求结束观察角色，再立即请求结束恢复角色，两次请求之间不等待前者结束。最终24次双角色故障注入的请求间隔均不超过0.191毫秒；这是相邻请求，**不是原子的“同时终止”**。两个进程退出后没有第三个角色清除调试寄存器。

脚本对仍存活的自己的子进程查询调试关系；非并行场景另成对调用暂停/读取上下文/恢复，只保存槽是否启用、是否指向夹具及暂停计数，不改寄存器。随后要求新的主线程/新线程调用和连续心跳；并行场景由3个工作线程自主连续调用，不等待修复。

[503结果](evidence/503-bounded-receive-dual-loss.json)的最终命令为 `python docs/experiments/test_receive_probe_dual_loss.py --repeat 3`，**退出码1，18通过、12失败**。首次30次同样18通过、12失败；第二批增加调试关系查询，没有改变恢复机制。

| 状态，每类3次 | 结果 |
| --- | --- |
| 无调试器、正常脱离 | 共6次继续运行 |
| 附加返回但尚未装入断点时双角色退出 | 3次继续运行，槽未启用 |
| 已就绪空闲、已收到命中事件、冻结清理但尚未清槽 | 共9次失败；调试关系已解除，但槽仍启用且指向夹具；后续调用因single-step异常退出1 |
| 自主并行调用中双角色退出 | 3次失败；工作线程报告single-step，无法完成3个工作线程，目标退出1 |
| 清槽后、解冻后、正常脱离后双角色退出 | 共9次继续运行，槽未启用 |

最后30次的调试关系查询均返回未被调试，包括12个失败场景；其中9次非并行失败直接读到仍启用的槽。查询语义依据微软 [CheckRemoteDebuggerPresent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-checkremotedebuggerpresent)；它不检查硬件断点，不能把返回false当作安全恢复完成。9次失败中的原有暂停计数为0、TF为false，冻结句柄退出时释放了本次暂停，但没有清除硬件执行断点。

这里的失败没有改成expected-failure或“故障检测通过”。正常清槽后的成功也不能证明清槽前故障安全。既有单角色恢复研究仍有效，但其前提是另一个保留调试对象的角色存活并成功执行清理。增加又一个用户态守护角色仍需证明最后一个角色退出后的状态，不能替代本项门槛。

## 应用断点先于附加断点

旧实现把首个 `EXCEPTION_BREAKPOINT` 当作附加断点，没有检查来源。微软 [DebugActiveProcess](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-debugactiveprocess)描述附加事件和初始断点，但没有提供本实验中ntdll导出地址组合的跨版本认证契约；[线程事件的起始地址](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-create_thread_debug_info)也只是可变更上下文下的近似信息。

为确定性构造先后顺序，审计观察器（历史源码路径 `experiments/receive_probe_attach_audit.py`，已删除）在本机观察到的ntdll break-in线程创建事件处增加一次计数暂停，让自建夹具主线程先触发应用断点，再在脱离后配对恢复，或确认目标已经退出。它没有向用户应用插入代码；本轮所有额外暂停、原生函数与异常都在自己的夹具中。这个受控次序不代表自然竞态发生率，也不用于暂停预算认证。

[504分类结果](evidence/504-bounded-receive-attach-classification.json)：

- 旧规则15次中9通过、6失败，命令退出1。6次抢先应用断点都被以 `DBG_CONTINUE` 处理并误记为初始断点，目标随后继续运行。3次应用直接调用同一 `DbgBreakPoint` 地址仍被误吞，说明单独比较地址不足。
- 新增可选实验候选，要求尚未识别初始断点、首次异常、地址与本机导出相符、且该线程的创建起点与本机break-in导出相符；其他断点交给原异常转发路径，并保持“尚未识别初始断点”。
- `python docs/experiments/test_receive_probe_attach_audit.py --strict --repeat 3` 退出0，15次对照通过。3次普通附加及有界匹配正常；6次抢先应用断点均使用 `DBG_EXCEPTION_NOT_HANDLED`，保持目标的断点异常退出语义；另外6次为无调试器基线和附加后应用断点对照。

该候选只使用同机同类Python夹具观察到的地址和线程来源，**不是远程模块身份认证，也不是可直接迁移到微信或其他Windows版本的分类器**。旧观察器保持不变，候选仅存在于专用审计程序的 `--strict-attach` 模式，未接入产品或原完整生命周期矩阵。

## 当前结论与后续

共享调试对象没有解决所有辅助进程退出后遗留硬件断点的问题。当前方法的实机推进到此不能通过门槛；初始分类候选的通过不抵消12项恢复失败。后续应先重新评估采集机制，候选必须给出“辅助进程全部退出后不留下可再次触发的目标断点”的可验证依据和最小夹具实验。尚未选定满足要求的新采集源，不能以增加守护层、缩短轮询、放宽失败预期或先绑微信PID代替解决。

日志/API内部失败、跨版本Native兼容性、真实模块/实例/最小化/随机标记绑定仍未完成；本轮没有继续这些后续实机步骤，也没有重跑产品、原完整原生套件或上一轮108项矩阵。

[505核查](evidence/505-bounded-receive-fault-validation.json)绑定4批90条原生结果（60通过、30失败，含两次重复确认的双角色失败），旧25份相关源码、29份产品、24份历史脚本、319份旧证据保持；新相关源码总数29。核查只是同一执行者的记录与哈希检查，不是恢复失败已修复，也不是独立审计。
