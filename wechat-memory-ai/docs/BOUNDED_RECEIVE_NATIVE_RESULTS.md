## 本轮实际实现

- [外部观察器](experiments/receive_probe_observer.py)：使用本机 System32 DbgEng，设置处理器执行断点，通过 RDX 读取限量虚构消息，保留方向/来源 unknown；支持命中上限、截止时间、取消、目标退出和有限清理。当前命令行只有 fixture 模式，没有微信入口。
- [自建原生夹具](experiments/receive_probe_fixture.py)：自己的 Python 子进程在自己的地址空间分配并调用 x64 小函数，向观察器提供虚构对象；另有新线程和异常路径。没有向其他进程注入代码。故意异常测试关闭该夹具自身的崩溃弹窗，不改系统设置。
- [集成检查](experiments/test_receive_probe_native.py)：启动、控制并清理本项目自己的夹具/观察器。观察器在附加前核对目标是同一 Python 可执行文件、父 PID 与测试脚本相同；本轮所有附加和内存读取都限于这些自建子进程。

观察记录只含测试匹配布尔、HMAC标签、计数和固定错误/HRESULT。原来的[17项虚构字节投影](experiments/check_receive_probe_layout.py)保持不变，未将固定测试标记当作实机随机标记。产品 `src/` 的29份文件保持0.1.22，没有接 Engine、模型、记忆或发送。

失败用例先让夹具执行一次未匹配消息并正常返回，确认观察器已经处理并恢复过一次真实断点；随后测试脚本强制结束**自己的观察器子进程**，再让夹具执行该函数。夹具最终输出 `OSError: exception: single step` 并以退出码1结束。不是用户微信崩溃，也不是仅仅缺少心跳或等待超时。测试保留为真正的失败，没有改成 expected-failure、放宽断言或用目标端异常捕获伪装恢复成功。

这里证明的是**当前实现不能在所测强制终止场景下保全目标后续执行**。本轮没有读取终止后的调试寄存器，不把具体残留寄存器或所有调试器的行为当成已证实事实。启用并读回 `DEBUG_PROCESS_DETACH_ON_EXIT | DEBUG_PROCESS_ONLY_THIS_PROCESS` 仍不足以让本用例通过；微软对[进程选项](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/debug-process-xxx)的说明不能替代这一实际恢复检查。

## 已定位和修复的实现问题

1. 初版头文件方法提取漏算3个 `STDMETHODV`，使 IDebugControl 后续槽位偏移。已改用具名接口映射，新增对固定头文件逐项核查。错误仅发生在自建夹具阶段，没有使用该版本连接微信。
2. 本机引擎尚无活动目标时设置进程选项返回 `E_UNEXPECTED`；现放在初始事件后设置并读回。明确设置初始中断选项后，附加才按预期完成；仅有 `AttachProcess` 返回成功不是已就绪。
3. 直接从硬件断点处分离，会将待处理的单步异常留给夹具。现移除断点后先把本观察器断点事件按 handled 继续，再驱动一次事件等待并分离。非本观察器异常仍按 not-handled 交还目标，两个异常用例覆盖此区别。
4. 有限 `WaitForEvent` 超时后，本机引擎可能报告逻辑 BREAK，但删除断点仍返回 `E_UNEXPECTED`，上下文并未可用。清理现在先恢复引擎 GO 状态，再请求 ACTIVE 中断，等实际事件可用后移除断点。中断请求返回成功本身不算清理成功。
5. 取消线程与引擎释放使用同一锁隔离，避免在已释放接口上调用中断；匹配分支也检查停顿预算。以上不修复观察器被强制结束的失败，因为该情形不执行正常清理代码。

接口依据为 [Microsoft/win32metadata 固定提交76c04c20](https://github.com/microsoft/win32metadata/blob/76c04c2021ef4a831a6f1e06d9566002d746139b/generation/WinSDK/RecompiledIdlHeaders/um/DbgEng.h)。原头文件只缓存在忽略的 `data/`，没有安装SDK、执行或提交第三方实现；本项目实验代码为自写。初版错误、修复与未解决项见[477实现核查](evidence/477-bounded-receive-implementation-validation.json)。

## 结论与继续边界

按用户批准方案“任何一项失败都不连接微信”的条件，**当前 DbgEng 观察器不得进入实机阶段**。没有向微信附加、读取其内存、操作窗口、提取密钥、读取聊天数据库、加载微信DLL、重启原监听或发送消息；本轮确实加载了系统调试库并读取了自建夹具内存，不能写成“没有任何进程操作”。

新鲜资源检查未发现本轮遗留的夹具或观察器进程。产品仍0.1.22、自动回复关闭，旧监听停止状态保持；额度最新已知剩余52%，既有id40不变。[478检查点](evidence/478-bounded-receive-native-checkpoint.json)保存这些边界。

已有授权持续有效，不重复询问。下一步仅在自建程序上研究强制终止时的恢复机制，并先让保留的失败用例通过；尚未运行的附加中途崩溃等边界仍须验证。不能仅用 finally、普通分离返回、目标暂时仍存活或独立守护进程的存在替代恢复证据，也不能改为跳过失败、软件断点、注入或放开真实发送。若无可验证恢复方式，应收敛当前观察方法，而不是继续扩大微信运行范围。
