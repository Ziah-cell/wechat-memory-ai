## 协议变化

新 v4 协议增加 `ABANDONED=7`。目标只登记一个已知自建写线程：挂起创建，原子发布其句柄，再恢复运行。句柄保留到 ACK 服务退出后才关闭。服务先验证连接和目标绑定，再检查此句柄；只有线程对象已终止、退出码查询成功且不属于正常返回的线程，才放弃通道。它不根据线程 ID、请求成功、超时或管道断开推断终止。

处理顺序为：确认实际线程对象终止 → 设置 ABANDONED → 保留写门原值 → 返回明确拒绝。不会抢回门、重新发布半写记录或重启采集。三个后续原调用仍执行并校验返回值，发布游标不再推进。正常结束线程不会误触发 abandoned。

这是 **ACK 请求触发的检测**，并不保证线程结束时立即发现；下一次有效 ACK 前的间隔没有上限。本轮也未实测线程查询权限失败、句柄查询失败或登记任意外部工作线程。

微软说明 `TerminateThread` 不给目标线程执行用户态代码的机会，并可能留下锁或进程状态问题。本实验仅结束停在自建屏障中的已知线程，不推导对任意线程使用该 API 的安全性。[TerminateThread 文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminatethread)

检测使用实际线程对象的等待结果，之后才读取其退出码，区分请求成功与实际结束。[等待语义](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject)、[退出码语义](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodethread)

## 真实执行结果

先提交 seq1–8，只 ACK 到 7。在第 9 次底层原函数返回后安排以下屏障。每个类别重复三次；线程退出码通过句柄实际读取为 73，主目标进程仍活。

| 结束位置 | 类别数 | publisher finally 已进入 | hook / worker finally | 写门 |
|---|---:|---:|---:|---:|
| 七个共享槽写入之前 | 7 | 0 | 0 / 0 | 1 |
| 偶数 stamp 和 published 更新之后 | 1 | 0 | 0 / 0 | 1 |
| 真实写 AV 过滤器返回之前 | 1 | 0 | 0 / 0 | 1 |
| 异常 finally 已停用、尚未解锁 | 1 | 1 | 0 / 0 | 1 |
| 已解锁、外围调用尚未返回 | 1 | 1 | 0 / 0 | 0 |

每次都保存准确的半写槽内容、暂停时 depth/armed、实际线程信号与退出码、请求状态、各层 finally 和外围返回计数。33 次被结束的外围调用均未返回，不能以底层原函数已返回来代替它。最终底层原函数成功返回总计 450 次；原函数返回值校验错误为 0。

两种正常释放对照分别从普通写屏障和真实 AV 过滤器释放；六次均有 publisher/hook/worker finally 和外围返回。普通路径提交 seq9 并确认；AV 路径停止采集但允许确认已提交前缀。

最终有 12 次真实共享写 AV，均记录 `0xc0000005`、write operation=1、固定 XCHG 地址及槽偏移 24，指令字节 `48 87 11`。控制页保持可写；故障样例的槽页只读。被结束在线程异常处理途中的调用，不算完整异常恢复成功。

目标收尾先确认写线程对象终止、再结束并 join ACK 服务，之后关闭线程句柄、恢复入口、删除展开表并释放映射。日志单独记录 `claimed_cooperative=false` 与未执行的 worker finally，避免把资源收尾描述成线程合作清理。

## 持久终态的范围

33 次写线程结束后，目标仍能处理命令和后续原调用。数据库此时拒绝 `reconcile`，返回 `target_alive`，会话仍为 active。目标进程合作结束后，既有对账才写入终态；所有证明均为 `same_process_signaled`，全部 `tail_unknown=true`。

因此，本阶段没有解决“目标长期存活，但采集通道已经放弃”的持久封口问题。它没有把工作线程结束伪装成源进程结束，也没有增加凭超时或 EOF 关会话的旁路。发布后屏障的三条 seq9 已完整发布并被观察，但未提交或 ACK，最终按协议记录为已观测丢弃。

## 保留的失败和审计

先运行缺少死亡检测的精确变体，实际线程退出 73 后仍 ACTIVE、gate=1、三层 finally 均 0，正确断言失败。加入服务检测后，七项代表样例通过。再按正确断言执行两轮负对照，每轮四项均失败：

| 负对照 | 实际问题 |
|---|---|
| 遗漏死亡检测 | 线程已结束仍返回 busy，通道未 abandoned |
| 擅自清除遗留门 | gate 从 1 被清为 0，违反通道放弃约定 |
| 将活线程判死 | 句柄仍 WAIT_TIMEOUT 时提前回复 abandoned |
| 伪报合作清理 | worker finally=0，却声称 cooperative=true |

全部 **55 项原生尝试，46 项匹配、9 项失败**；缺实现预检另列。两次编译均成功，完整输入与 EXE 保留。最终矩阵和末轮负对照使用同一 EXE，失败没有改写为 expected-failure。

独立审计不导入被测模块，核对原始线程/进程/ACK 日志，并复制 DB/WAL/SHM 后只读核查。全量 165 个进程退出码齐全且均为 0，47 个线程被强制结束、8 个正常释放；55 库 444 行、55 个终态、67 次有提交回执的成功 ACK、134 次 abandoned 回复。原始数据库哈希不变。

原 83 份研究源码、29 份产品源码、24 份分析脚本、371 份证据及 806 个受保护旧文件保持。Git 保存新源码、报告和证据 JSON；本机忽略目录中的编译器、EXE、数据库、日志以哈希追踪，未声称这些二进制与原始文件已经上传。新源码分别记录本地原字节和 Git LF blob 哈希。
