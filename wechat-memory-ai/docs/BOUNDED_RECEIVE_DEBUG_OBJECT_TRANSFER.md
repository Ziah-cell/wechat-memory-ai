# 保留调试对象后的故障接手实验

2026-10-09。延续[475授权](evidence/475-bounded-receive-authorization.json)，在自建程序上增加第四种恢复办法：安装断点前，由恢复进程创建并保留同一个内核调试对象，再把句柄复制给实际执行附加的观察进程。**最终13种场景各运行3次，39次符合预期：36次继续运行，3次保留故意触发的原生致命异常。** 这是单线程恢复机制的进展，尚不是通过完整准入检查的微信观察器。

## 与上一轮的区别

[上一轮三种办法](BOUNDED_RECEIVE_METHOD_COMPARISON.md)均未覆盖真正持有断点的调试进程被强制结束。单独增加一个事后修复进程，还要抢在目标下一次执行前清除断点；前端与调试器分离，也只改善前端退出。

本次恢复进程在附加之前持有同一调试对象的引用。观察进程退出后，这个引用在本机实测中保留了调试关系及未交付事件，目标下一次命中断点会等待事件处理。恢复进程**故意延迟200毫秒**才接手；测试在结束观察进程后立即请求下一次调用，或让目标自主连续调用，均没有等待恢复完成才发起调用。200毫秒是故障注入条件，不是满足原方案100毫秒停顿预算的证明。

两个角色及目标都是测试脚本创建的子进程。恢复进程先验证同级进程身份及目标四字节虚构函数，随后才复制自己的调试对象句柄；不枚举系统句柄，不选择或附加用户应用。观察进程监测恢复进程的存活，后者单独退出时，前者执行正常清理。

实现见 [receive_probe_transfer.py](experiments/receive_probe_transfer.py)，测试见 [test_receive_probe_transfer.py](experiments/test_receive_probe_transfer.py)。没有改变产品代码或原 DbgEng 观察器，没有软件断点补丁、自定义 DLL 注入或微信运行入口。

## 失败对照及修正

初版15次对照中12次恢复、3次失败。失败均位于 `WaitForDebugEvent` 已把硬件异常交给观察进程、但尚未继续事件的边界：恢复进程再等待时取不到这个已经交付的事件，直接清除断点并脱离虽然返回成功，目标仍以单步异常退出。该结果保存在[486](evidence/486-bounded-receive-debug-object-transfer.json)，没有因后来的成功覆盖。

修正是对已知的夹具主线程请求 `DBG_REPLY_LATER`，要求重新报告尚未回复的事件；随后重新等待并依据实际返回的异常种类处理。自己的硬件异常按正常路径恢复，无关异常仍交回目标。它不从 RIP 或寄存器残留猜异常种类，也不把未知事件统一标为已处理。收到异常后、修改 RF 后、已经继续执行后分别注入退出；无关可处理异常仍到达目标处理器，另一原生线程上的 UD2 仍使目标以 `0xc000001d` 退出。最后一种情况证明异常未被吞掉，不代表新线程的硬件断点或事件重报已覆盖。

加上事件重报后，第一组扩展27次对照符合预期。继续检查附加及正常结束时，又发现3类各3次清理状态错误：尚未安装断点时不能要求 DR0 已指向目标；观察进程已正常脱离时不能再次当成仍附加。没有将这些错误说成目标崩溃或自动恢复成功。

最终版在暂停的夹具主线程检查实际启用槽，未启用时无需清除；启用时仅接受本实验的槽0。对正常结束的观察进程，额外检查目标已无调试器且没有启用的调试槽，才返回 `already_detached`。测试仍要求新的函数调用和增长的心跳；没有仅放宽一个返回值。各失败版本、源码哈希及修正后的结果见[487](evidence/487-bounded-receive-transfer-lifecycle.json)。

## 最终实际结果

运行 `python docs/experiments/test_receive_probe_transfer.py --replay`，退出码0。

| 场景 | 次数 | 实际结果 |
| --- | ---: | --- |
| 首次命中前结束观察进程；下一调用立即发起 | 3 | 恢复 |
| 已返回一次调用后结束；下一调用立即发起 | 3 | 恢复 |
| 自主连续调用期间结束观察进程 | 3 | 恢复并完成连续调用 |
| 已收到自己的断点事件，尚未处理时结束 | 3 | 事件重报，恢复 |
| 已修改 RF、尚未继续事件时结束 | 3 | 事件重报，恢复 |
| 已继续事件后结束 | 3 | 恢复 |
| 可处理的无关异常已收到时结束 | 3 | 目标原处理器收到异常，随后恢复 |
| 另一原生线程的 UD2 异常已收到时结束 | 3 | 保留预期致命退出码，不算恢复 |
| 自主连续调用期间仅结束恢复进程 | 3 | 存活观察进程取消并正常脱离 |
| 附加 API 已成功，尚未进入事件循环时结束 | 3 | 恢复 |
| 初始事件已收到，写断点前结束 | 3 | 恢复 |
| 断点刚写入、armed 状态尚未更新时结束 | 3 | 恢复 |
| 正常达到200次命中预算并退出 | 3 | 确认已脱离且槽未启用，目标继续运行 |

这些是有限调度样本，不证明所有指令间隙、系统版本或双进程同时故障。原先失败的 DbgEng 强制退出测试没有被改成预期失败，也没有被这个不同实现的39次结果替代。

## 依据和未完成的条件

创建及绑定调试对象的声明来自固定提交的 [System Informer phnt/ntdbg.h](https://github.com/winsiderss/systeminformer/blob/9cdd0426e0843e80cabef27f148cee0281fa0883/phnt/include/ntdbg.h)，属于第三方 Native API 声明，**不是微软支持或稳定性的保证**。本轮只保存头文件作比对，没有安装或执行该项目。系统句柄复制见微软 [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle)；其文档不能单独证明调试对象跨进程接手受支持。事件重报及异常处理状态见 [ContinueDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent)，附加状态检查见 [CheckRemoteDebuggerPresent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-checkremotedebuggerpresent)。上述文档说明接口；跨进程使用效果仅以本次夹具结果为依据。

进入微信前仍需完成同一最终实现的新线程/线程退出恢复、有界字段读取和脱敏、延迟事件、布局与读取预算、取消与目标退出、正常及故障停顿预算、身份及模块绑定，并重新验证完整准入集合。当前重报只针对已知主线程；原生新线程 UD2 对照不能代替新线程接收覆盖。两个调试角色同时终止、系统调用中途故障和系统升级后的 Native API 兼容性未验证。不能直接把当前脚本改成接受微信 PID 就开始实测。
