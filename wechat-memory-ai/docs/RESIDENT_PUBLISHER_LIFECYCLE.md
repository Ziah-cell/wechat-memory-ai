# 自建原生发布器：消费者故障隔离与交付边界

2026-10-10。**目标持有发布代码和缓冲的有限夹具通过了消费者故障隔离检查；它还不是微信消息源，也不是完整 Hook。** 消费者停止读取、正常关闭或被强制结束后，目标自主工作线程继续执行原函数。固定容量耗尽、竞争及无效长度会停止采集，后续原调用继续。

最终20类场景各3次，共60次观察符合断言：54次机制检查，6次刻意确认交付限制。不能把60次写成消息完整性、只交付一次、硬延迟或实机兼容验收通过。此前[跳板展开研究](RESIDENT_RECEIVE_FEASIBILITY.md)没有在本轮接成 Hook；旧[硬件断点双角色退出失败](BOUNDED_RECEIVE_FAULT_BOUNDARIES.md)也没有改变。

## 实现与资源所有权

C夹具（历史源码路径 `experiments/resident_publisher_fixture.c`，已删除）是编译的 Windows x64 可执行程序。目标合作启动后直接调用 `wrapped → publish → original`；发布代码随目标程序驻留，没有第三方 DLL、动态跳板、入口补丁或调试寄存器。测试的签名和输入完全已知，不能外推真实微信 ABI。

- 目标创建4096字节、分页文件支持的具名映射，布局占392字节：头部72字节，加8条40字节记录（序号8字节、虚构载荷32字节）。记录区单会话只追加、不覆写、不循环复用。它不适合直接承担持续收信。
- 状态和已发布数量采用本次编译器支持的原生无锁原子操作。发布者仅尝试一次取得目标内的写入门闩；竞争时将会话置为故障，自己仍转发原调用。写完一条后才发布数量。停止时不释放回调所需资源；已进入回调可能完成一次写入，但消费者会拒绝非活动会话。
- 消费者以 `FILE_MAP_READ` 映射；每次启动实际用 `VirtualQuery` 核验 `PAGE_READONLY`。没有写入测试，没有建立针对恶意同用户进程的权限隔离。官方接口说明只读视图写入会触发访问违例，跨进程映射视图保持一致；指针不能作为共享地址协议。[映射接口](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile)。
- 消费者不回写游标、不占目标门闩、不给目标提供必须存活的地址、句柄或代码。目标发布路径没有分配、输出、文件/网络操作、消费者查询或重试循环。**无外部等待不等于调度、缺页、CPU争用及程序故障都有硬时间上限。** 本轮记录整场景耗时，没有单回调停顿预算数据。
- 会话使用随机128位代次，并绑定目标 PID 和进程创建时间。发现同名映射已经存在时，新目标拒绝启动，不清零旧映射。消费者持有进程句柄，并在接受副本前复核进程未退出、会话仍活动。

消费者尚持有视图时，目标退出后映射可以继续存在。实测此时新目标同名创建被拒；最后一个消费者释放后，同名新目标可创建空会话。不能把旧页仍可读当作旧目标仍活着。[创建及同名对象语义](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-createfilemappingw)、[映射与句柄清理](https://learn.microsoft.com/en-us/windows/win32/memory/closing-a-file-mapping-object)。

编译参数为 `zig cc -target x86_64-windows-gnu -std=c11 -O2 -Wall -Wextra -Werror`。最终C源SHA256为 `882328c3fcfa9b65fb368107176c273e7e3d0ebe35fefce6f39112e19ab71971`，可执行文件SHA256为 `9c5225def798ea77507dce2643282479869c35fb5e49cc7841a50512b4e41307`。初次普通编译和随后加 `noinline` 的版本均完整保存；原生矩阵使用后者。

同一源码和优化参数的编译器汇编列表确认 `wrapped` 实际调用 `publish` 和 `original` 并比较返回值；发布函数没有调用指令或向后分支。列表是编译输出，**不是运行时指令跟踪或最终PE逐字节反汇编**。一次辅助检查因默认Python环境没有pefile而未运行；随后标准库只读解析确认PE为x64、无COFF符号表，没有因此声称完成二进制符号核查。

最终批次创建138个自己的子进程，全部退出：108次正常0、18次由测试结束为1、9次同名拒绝10、3次代次拒绝11。18次强制结束包含3个目标和15个消费者。各目标最后状态累计记录649,902次原调用；最终批次场景耗时合计约30.814秒。这些计数不代表完整消息处理量或实时性能保证。

发布者并行故障测试使用一个固定锁竞争注入点和真正4线程调用，未声称覆盖每条指令边界。消费者不响应测试是停止消费/持有副本，没有冻结其所有OS线程或刻意填满输出管道。控制测试的Python父进程始终存活，**没有证明所有外部测试辅助进程同时崩溃后的完整目标生命周期**。

## 两个交付限制及失败对照

1. **停止不能撤回已经接受的输出。** 消费者在最后复核之后，目标仍可能停止或退出；输出也可能已在管道中等待接收。停止发生在复制与提交之间时，本实现拒绝副本；已经提交的那条仍存在。真正交付端需要撤销屏障和停止确认语义，不能再叠一次状态读取便宣称零迟到交付。
2. **同代次重连会重放。** 每个新消费者游标从0开始，重新连接同一活动会话会再次读到1–3。序号和代次提供判重键，但目前没有跨消费者进程的持久提交游标，也没有产品桥接或发送端去重。这是未解决限制，不改成“只交付一次通过”。

为确认检查有效，单独复制最终C源，只删除消费者提交前的最后一次状态/进程复核，另编译故障二进制；原断言未变。在“复制后停止”和“复制后目标被杀”两例中，它都错误返回旧1–3条，测试0/2、驱动退出1。原始观察、故障源码、二进制哈希全部保留。正式二进制未改。
