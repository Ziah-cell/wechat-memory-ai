# 有界观察的停顿计时与预算实验

2026-10-09。延续[授权](evidence/475-bounded-receive-authorization.json)和[多线程夹具结果](BOUNDED_RECEIVE_GUARDED_THREADS.md)，本轮确认旧事件处理计时会漏掉大部分接管停顿，并为自建夹具加入跨进程计时、保守区间预算和超限清理。最终12类各3次，**36次检查符合预期且夹具均恢复运行**：9次普通观察在保守预算内，21次上界超预算后丢弃记录，6次计时历史不可用时报告未知。它们不是36次“性能通过”，也不是微信实机验收。

## 实际测量什么

夹具在原生函数前后读取 `perf_counter_ns`，另有线程约每2毫秒记录一次执行时间点。调用耗时与执行间隙包括正常运行、等待和系统调度，不能全部归因于调试暂停；也不能把单个心跳线程当作每个线程都恢复的证据。测试另要求新的主/新线程调用成功。

观察角色和恢复角色在附加、等待事件、继续事件、冻结、解冻及脱离前后记录同一时钟的时间戳。跨进程时钟依据 Python 的 [perf_counter 文档](https://docs.python.org/3/library/time.html#time.perf_counter)；Windows计时与跨线程一时钟单位的顺序歧义参考微软 [QPC说明](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)。运算使用整数纳秒，最终才换算毫秒；本机比较使用1微秒边界余量。换机器需核对时钟精度，不能直接移植这一固定余量。

依据调试事件使目标线程暂停、等待继续的[微软说明](https://learn.microsoft.com/en-us/windows/win32/debug/debugging-events)，统计两层边界：

- **已知停顿下界**：事件已返回到观察器后，至调用继续之前；冻结已成功后，至开始关闭本次状态句柄之前。继续请求重报时结束该段，收到重报事件后重新开始，不把中间状态猜成连续暂停。
- **保守上界**：从前一继续调用开始，或最近一次未取得事件的等待调用开始，至下一次继续返回；另加附加、脱离、冻结/解冻的API外侧区间。采用未取得事件的等待**开始**时间，避免把排队或调度延迟排除。重叠区间取并集，不按线程或角色重复累加。

下界已超过100毫秒/累计1秒，可以确认已测部分超限；上界在阈值内，只能说当前记录支持的保守边界在内；上下界跨过阈值时保持无法认证。未知、未闭合或与目标执行时间点矛盾的记录不能成为通过。这里没有内核调度跟踪，**没有精确测得每段内核暂停的起止**。事件队列、共享调试对象及状态句柄的适用假设仍受前述夹具研究范围限制；等待接口本身不提供事件发生时间戳，见 [WaitForDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-waitfordebugevent)。

## 实现及故障历史

新增[计时观察器](experiments/receive_probe_timing.py)是已有夹具观察器的实验子类；[计时夹具](experiments/receive_probe_timed_fixture.py)记录虚构函数的调用区间；[区间计算器](experiments/receive_pause_bounds.py)负责并集和判定。既有15份观察/夹具相关源码与产品代码保持原样，没有微信运行入口。

[495对照](evidence/495-bounded-receive-timing-basis.json)保留三次预期失败：观察进程在事件已收到时退出，恢复角色仍按原实验条件故意延迟200毫秒接手；目标调用分别耗时216.901、218.093、218.237毫秒，而旧事件处理报告仅0.317、0.390、0.243毫秒。恢复成功不代表停顿满足预算。

只测量、不执行新预算的首轮9次验证捕获了处理函数外的150毫秒延迟、冻结清理延迟，以及20次约60毫秒事件累积约1.21秒。最初的“排队”注入发生在初始附加事件尚未完全结束时，目标执行间隙变长，但标记函数本身没有长耗时；后续改为先完成一次非标记调用，再在下一次等待前注入延迟，最终标记调用约181毫秒。没有拿原来的场景证明它未覆盖的时序。

启用预算检查后首轮9次中7次通过、2次失败。附加超限已经在就绪前触发退出，测试仍在等 `armed`，因此更正测试路径，未提前发送输入。另一项暴露恢复角色只计算自身事件、漏掉原观察角色历史；增加限定在测试缓存目录内的计时日志，恢复角色确认原进程退出后才读取，合并同一时钟的区间。日志有记录数/大小/结构/序列检查，不含目标正文、指针或密钥；当前研究缓存保留夹具线程号，编号证据只保存相对时间摘要。

扩展33次中30次通过，3次截断日志检查失败：Windows文本换行转换把残留的CR也当作换行，截掉LF后未被拒绝。修正为先检查原始字节的末尾LF，再解码。增加缺失/截断、结构和角色校验；缺失历史会得到 `pause_timing_unknown`，完成清理但不给出可用记录。[496结果](evidence/496-bounded-receive-timing-results.json)保留所有失败，不覆盖原文件。

日志和标准输出都产生额外开销，这些开销包含在测量区间里；本轮没有把该日志方式当作可直接部署的长期采集架构。原生调用或日志写入本身阻塞时，Python无法保证及时执行下一次预算检查；预算仍是超限后请求清理的政策，不是系统调用或故障停顿的硬实时保证。

## 最终结果

执行 `python docs/experiments/test_receive_probe_timing.py --enforce --repeat 3`，退出码0。以下每类均运行3次；数值为该组的实测范围或摘要。

| --- | --- | --- |

| 空闲250毫秒后匹配 | 单段上界70.10–75.62毫秒 | 空闲时间未整段算成停顿，恢复 |
| 新线程匹配 | 单段上界7.98–10.70毫秒 | 有界匹配，恢复 |

整合所有测试端记录后的离线判定为9次在保守边界内、15次已知下界超限、12次上下界无法认证。最后两类的测试控制器仍持有完整输出，所以能离线测到超限；这不能替恢复角色补造运行时缺失的历史。

[14项离线检查](experiments/test_receive_pause_bounds.py)通过，覆盖区间重叠/相邻、倒序拒绝、冻结重叠、未闭合、序列缺口、目标执行与已知停止矛盾、等待开始边界、累计上限、重报间隙，以及Windows日志边界和结构。36次原生测试没有发现目标执行点落在已知停止区间内部；这是所采样线程的交叉检查，不是独立内核测量。

## 当前边界和后续

本轮完成的是**夹具计时与保守预算请求机制**。明确区分性能通过、检测超限和未知后拒绝，没有放宽原100毫秒/1秒阈值。故意注入的长停顿证明检测和清理路径，不应删除这些失败条件以宣称所有故障都能在100毫秒内恢复。

进入微信前还需处理初始断点分类、日志/原生调用故障和双角色同时退出，核查Native API兼容性，并把该计时机制与原完整生命周期集合重新集成验证；本轮36次定向计时检查没有替代上一轮108次完整生命周期矩阵。之后再完成真实实例、固定模块/入口、真正最小化状态及本次随机标记绑定。仍无实机运行入口，不请求测试消息，不启用发送、模型或记忆。

[497核查](evidence/497-bounded-receive-timing-validation.json)绑定6批99次原生记录、14项最终离线检查及20份相关源码，保留311份旧证据、29份产品源码和24份旧脚本。未重跑产品或原完整原生回归。[498检查点](evidence/498-bounded-receive-timing-checkpoint.json)保持产品0.1.22、自动回复关闭、旧监听保存停止；本轮仅调试自建进程，没有微信、窗口、密钥、聊天库、真实发送或Jev操作。
