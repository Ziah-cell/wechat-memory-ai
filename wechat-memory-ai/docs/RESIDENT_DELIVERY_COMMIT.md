# 虚构持久接收表：重启去重与停止提交顺序

2026-10-10。**在自建持久接收表范围内，消费者重启后重复批次不再产生重复行；停止事务确认后，该会话不能再插入记录。** 最终17类各3次，共51次检查通过，包括真实原生消费者重连、接收进程强制退出、丢失确认重试及两个进程争用事务。

这里的“接收”仅指新增实验SQLite中的一行。没有真实消息发送、模型调用、产品Store或微信接入；不能将数据库的原子提交外推成网络发送恰好一次。停止也不删除既有行或撤回已经提交的记录。

## 对上一阶段的具体补充

[上一阶段](RESIDENT_PUBLISHER_LIFECYCLE.md)原生消费者重连会从序号0开始，且已经输出的记录不可撤回。本轮保留它的代码和二进制，增加两个独立研究文件：接收表实现（历史源码路径 `experiments/resident_delivery_ledger.py`，已删除）与多进程测试驱动（历史源码路径 `experiments/test_resident_delivery.py`，已删除）。数据库仅允许创建在本阶段忽略目录，载荷仅接受固定虚构结构；没有打开真实聊天库或产品数据库。

原生目标、只读消费者继续由测试控制器创建。控制器把已绑定的实验会话号和消费者记录送入接收进程；**这不是实际来源认证协议**，也不允许把未认证微信字段当作已认证来信。原生发布回调不访问SQLite，不等待接收端、磁盘或停止确认。

接收进程保存四张表：会话状态与游标、当前会话、操作顺序、接收记录。`(epoch, seq)` 是接收记录的主键；重复键还必须载荷相同。序号缺口、同键不同载荷和非法批次都会拒绝；不会用忽略冲突的INSERT掩盖不一致。新行、游标和提交操作号一起提交。

停止和接收都使用 `BEGIN IMMEDIATE`。SQLite同一数据库同时只能有一个写事务；申请失败时返回忙碌，本实现不假装成功，也不在原生目标回调中重试。[事务规则](https://www.sqlite.org/lang_transaction.html)。

因此操作顺序有两种：接收先拿到写锁并提交，则行在停止操作号之前；停止先提交，则后来接收读到关闭状态并拒绝。成功ACK只在COMMIT完成后输出。接收表重开后保留状态；关闭的代次不能重新创建，同一个旧STOP重试返回原操作号，迟到的旧STOP也不会关闭新代次。

## 真实崩溃及并发结果

使用运行时Python 3.12.14、SQLite **3.53.1**，每个连接核验WAL及 `synchronous=FULL`。官方说明WAL文件属于持久状态，不应单独删除或与数据库拆开保存；本轮未手动删除WAL。[WAL机制和文件寿命](https://www.sqlite.org/wal.html)。官方记录的WAL-reset问题在3.51.3及以后修复；当前夹具拒绝更旧版本，不声称测试了所有回补版本。[修复版本依据](https://www.sqlite.org/wal.html)。FULL同步设置不代替硬件及断电验证；本轮只测试进程结束与重开。[同步设置](https://www.sqlite.org/pragma.html#pragma_synchronous)。

最终批次共105个自建进程：84个Python接收进程、9个原生目标、12个原生消费者。90次正常退出0，15次由测试强制结束为1，全部已退出。51个独立实验数据库保留；目标最后状态合计333次原调用。场景耗时合计约11.410秒，仅是测试耗时，不是回调性能或硬停止上限。

进程退出、WAL/SHM均已正常清理后，另用只读不可变连接逐库审计：51库共72行，完整性检查均为ok，行序号与持久游标连续，关闭会话的全部行提交号都早于STOP；审计前后数据库哈希相同。不可变模式仅用于这些已停止写入的归档，不用于活动数据库。[只读URI语义](https://www.sqlite.org/uri.html)。

事务检查点只在外部接收夹具中，分别暂停于已执行事务写入但尚未COMMIT、以及COMMIT已返回但尚未输出ACK。控制器实际结束该进程，然后重开相同数据库核查；没有用内存模拟代替持久化。但未注入每一个系统调用边界，也未做掉电、磁盘故障、损坏数据库或跨机器文件系统测试。

## 保留的失败及停止语义

五批共70项：67项符合原断言，3项失败均保留。初次实现不存在时，Python缺文件输出令JSON读取失败；首批实现14项通过。补充3项时有2项通过，非对象JSON触发未处理异常，驱动读到Traceback而失败，并在清理时结束该进程；修复为明确协议拒绝后，最终51项通过。

另复制最终源码，**只删除活动/当前代次检查**，使用原“停止后积压原生批次”断言运行：STOP成功后仍插入3行，测试失败，驱动退出1。没有改成预期通过，正式实现未改。原阶段的硬件断点退出失败也保持。

STOP确认后的保证是“没有新的接收行提交”，不是“以后收不到任何成功回执”。接收先提交而ACK因调度迟到时，STOP可能先返回；该较早提交的ACK依然可以出现。测试明确验证这个顺序。将来真正交付到其他系统还需自己的幂等键、提交确认和停止语义；已有接收行之后是否执行模型/发送，本轮没有实现或授权。
