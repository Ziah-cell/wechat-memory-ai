## 持门期间的故障

新 guarded_publish 保留固定8条、32字节按值候选、满/忙即停止的结构。原函数成功返回后才进入发布器；先检查状态与长度，再以CAS取得写门。持门区使用 try/finally，无循环等待、分配或外部I/O。四个注入点都通过旧汇编复制函数读取本进程的NOACCESS页，产生真实访问违例；窄过滤器仍要求自身复制指令范围、读操作和自身保护页地址。

**这里中断的是共享记录写入过程中的指定读指令，不是让共享记录写指令或原子提交指令自身出错。** 没有改共享映射的页保护，不能证明任意写错误、对象失效或内存损坏安全。finally 释放门之后，由Hook异常处理器把采集状态设为 INVALID；此顺序尚未与第二个并发生产者交错验证，不能当作原子停止屏障。

每个场景结束后再做一次正常调用。四个故障场景均保留两次原返回、状态INVALID、写门0、主线程深度0，后续消费者因停用拒绝输出。

## 确定重叠的线程检查

场景值及深度都使用线程局部存储。测试专用事件让线程1在外层Hook深度1、候选复制之前等待；控制线程收到已进入事件后创建线程2。线程2完成一次含嵌套调用的外层调用，检查自身深度恢复，再放行线程1。两个线程均join并确认退出0后，控制线程才输出槽内容和状态。因此重叠来自实际事件顺序，不依靠调度碰运气；等待在写门区之外，但它仍是阻塞测试插桩，不是生产热路径或时延保证。

正常重入时，线程2的id2先提交、线程1的id1后提交，再由控制线程提交id3；库内序号1、2、3对应id2、id1、id3。线程1重入原函数异常时，该异常继续传播到工作线程外层SEH；线程1不发布id1，后续库内是id2、id3。两种场景均检查不同线程ID、两个工作线程深度均恢复为0，以及位置加权的原返回结果。

最终6个TLS场景实际创建12个工作线程。正常场景共5次Hook进入/成功原返回；异常场景共5次进入、3次成功原返回、1次原异常传播。每种各跳过2个嵌套候选，仍然存在主动漏掉嵌套记录的策略限制。原返回计数在Hook接到返回值后增加，不是原函数体内独立计数。
